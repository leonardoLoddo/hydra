# Configuration

Hydra stores shared project policy in `.hydra.json`. Review and version this
file. Do not version or manually edit Hydra's machine-local locator, inventory,
ownership marker, pending records, recovery records, or lock.

## Current schema

A configuration generated by `hydra init` has this form:

```json
{
  "version": 2,
  "projectId": "shop-0123456789abcdef0123456789abcdef",
  "headsDirectory": {
    "strategy": "sibling",
    "suffix": ".heads"
  },
  "branchPrefix": "hydra/",
  "storage": {
    "mode": "auto"
  },
  "overlay": {
    "copy": [
      "... .gitignore"
    ]
  }
}
```

The project schema version must be `2`. The experimental version 1 format is
not supported or migrated.

Hydra uses strict JSON:

- comments are not allowed;
- unknown fields are rejected;
- fields belonging to another strategy are rejected;
- `$schema` is currently rejected because Hydra has not published an editor
  schema.

## Project identity

`projectId` is generated once and identifies the same project across machines.
Treat it as opaque and do not edit it.

Each machine also has a separate local `installationId` in unversioned state.
The shared project ID does not authorize one installation to claim another
installation's Heads directory.

## Heads directory policy

The versioned `headsDirectory` field stores a portable policy. The actual
canonical path for one machine is stored only in the local locator.

### Sibling strategy

This is the policy generated by `hydra init`:

```json
{
  "strategy": "sibling",
  "suffix": ".heads"
}
```

For `/workspace/Shop`, it resolves `/workspace/Shop.heads`.

The suffix is a filename fragment, not a path. It may contain spaces, Unicode,
and punctuation, but it must be non-empty and cannot contain control
characters, `/`, or `\`.

Valid examples include:

```json
{"strategy": "sibling", "suffix": "heads"}
```

```json
{"strategy": "sibling", "suffix": " workspace 🚀"}
```

### Relative strategy

The configuration reader also understands:

```json
{
  "strategy": "relative",
  "base": "repositoryParent",
  "path": "workspaces/shop-heads"
}
```

The path is interpreted relative to the directory containing the canonical
parent repository. It uses `/` as the portable separator, must not be absolute,
and cannot contain empty, `.` or `..` components.

### Local strategy

The reader also understands:

```json
{
  "strategy": "local"
}
```

The absolute destination then exists only in the machine-local locator.

`hydra init` creates only the `sibling` strategy. Do not switch an initialized
project to `relative` or `local` by editing configuration or local metadata.
Hydra detects a policy/locator mismatch and refuses state mutation.

Every resolved destination must remain outside the parent repository and every
registered worktree, and it must belong to the current local installation.

## Private branch prefix

`branchPrefix` is prepended to the Head name:

```json
{
  "branchPrefix": "hydra/"
}
```

The Head `payment` therefore uses `refs/heads/hydra/payment`. The resulting
full branch name must be valid in Git and unused.

Changing the prefix does not rename existing private branches or migrate local
inventory. Treat it as creation policy and do not change it casually in a
project with existing Heads.

## Storage policy

The default is:

```json
{
  "storage": {
    "mode": "auto"
  }
}
```

`auto` tries native copy-on-write on the real destination volume and falls
back to an isolated full copy.

To force deterministic full-copy materialization for regular tracked and
overlay files, use:

```json
{
  "storage": {
    "mode": "copy"
  }
}
```

This mode does not waive the explicit prompt for the logical cost of non-empty
overlay files.

See [Storage and overlays](storage-and-overlays.md).

## Overlay policy

`overlay.copy` is an ordered selection list using Gitignore semantics plus
Hydra's `... <rules-file>` expansion:

```json
{
  "overlay": {
    "copy": [
      "... .gitignore",
      ".tool-cache/",
      "!.tool-cache/private/"
    ]
  }
}
```

The last matching rule wins. A confirmed unsafe-symlink exclusion is appended
as a literal root-anchored negative rule so it overrides earlier selection.

## Open command adapter

Hydra has no default editor. Configure one explicitly:

```json
{
  "commands": {
    "open": {
      "program": "code",
      "args": ["{path}"]
    }
  }
}
```

`hydra head open <name>` validates the Head, starts this program from the Head
directory, inherits the terminal streams, and waits for its exit status.

## Close behavior

When `commands.close` is absent, Hydra uses native local Git integration and
protected removal. Conceptually, the defaults are merge integration with
removal on success.

To replace native integration with a project command:

```json
{
  "commands": {
    "close": {
      "strategy": "command",
      "program": "./tools/close-head",
      "args": ["{path}", "{headRef}", "{targetRef}"],
      "removeOnSuccess": true
    }
  }
}
```

`removeOnSuccess` is required for the command strategy:

- `false` preserves worktree, private branch, and inventory after exit code 0;
- `true` asks Hydra to run ordinary protected removal after exit code 0.

Protected removal still requires a clean, consistent Head whose commits are
integrated into the target. A custom command cannot bypass those checks.

### Verification-only close adapter

For a Rust project, close can run a gate and preserve the Head:

```json
{
  "commands": {
    "close": {
      "strategy": "command",
      "program": "cargo",
      "args": ["test", "--workspace"],
      "removeOnSuccess": false
    }
  }
}
```

### Pull-request adapter

A versioned script can publish a branch and open a pull request:

```json
{
  "commands": {
    "close": {
      "strategy": "command",
      "program": "./tools/open-head-pr",
      "args": ["{headRef}", "{targetRef}"],
      "removeOnSuccess": false
    }
  }
}
```

For example, `tools/open-head-pr` could contain:

```bash
#!/usr/bin/env bash
set -euo pipefail

head_branch=${1#refs/heads/}
target_branch=${2#refs/heads/}

git push --set-upstream origin "$head_branch"
gh pr create --head "$head_branch" --base "$target_branch"
```

Make the script executable and review both files before committing them:

```bash
chmod +x tools/open-head-pr
git add tools/open-head-pr .hydra.json
git commit -m "chore: configure Hydra pull request workflow"
```

This example requires GitHub CLI to be installed and authenticated.
The script is responsible for Git hosting authentication, push behavior, and
pull-request creation. Hydra cannot undo a successful push if a later external
step fails.

If a custom command requests `removeOnSuccess: true`, it must leave the Head
clean and make the private Head commit reachable from the recorded target
before returning exit code zero. Prefer native close for normal local Git
integration because it already protects checked-out target worktrees and ref
publication.

## Adapter placeholders and process safety

Open and command-based close adapters support:

- `{name}`;
- `{path}`;
- `{headRef}`;
- `{baseRef}`;
- `{targetRef}`.

A placeholder may appear inside one argument, such as `--folder={path}`.
Unknown or unbalanced braces and NUL bytes are rejected before process launch.
Braces inside an expanded value remain literal and are not evaluated again.

Hydra passes `program` and every `args` element separately; it does not build
an unescaped shell command. The program is nevertheless trusted project code,
not sandboxed code. Review configuration before running `head open` or
command-based `head close`.

## Local state is not configuration

These paths are machine-local implementation state:

```text
<git-common-dir>/hydra/project.json
<heads-directory>/.hydra/directory.json
<heads-directory>/.hydra/heads.json
<heads-directory>/.hydra/pending-<name>.json
<heads-directory>/.hydra/recovery-<name>.json
<git-private-worktree-directory>/hydra-head.json
```

Do not version, copy, symlink, or edit them. Use `hydra status` and
`hydra repair` when they disagree with Git.
